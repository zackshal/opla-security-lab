## 1 История исправлений и состояние

Во время первоначального развёртывания я столкнулся с ошибкой cloud-init на victim из-за отсутствия nginx. После подготовки образа все три ВМ показали status: done. Затем verifier отклонил арифметику ip+total; числовая проверка доступной длины позволила загрузить программу в native-режиме.

Исправлены нормализация JSON iproute2 с attached-массивом, декодирование u64/per-CPU, запуск переносимого C-теста при /tmp noexec и PATH /usr/sbin для bpftool при сборе версий. В рабочем GitLab история была объединена ранее; локальный коммит с обновлёнными материалами — `66a003a`. Публичный GitHub использует отдельную историю (`bca6d66` на момент подготовки миграции), поэтому перенос файлов не является подтверждением новых испытаний. Два HTTP burst и часть IDS/IPS-сценариев имеют локальные отчёты, но их нельзя автоматически приписывать всем режимам стенда.

## 3 Нагрузочные опыты

| Опыт / каталог reports | Δsyn | Δpass | Δdrop | Δmap_full | Δfragment_drop |

| SYN, scenario-syn-ynKwzUiD | 2004 | 509 | 1495 | 0 | 0 |
| ACK, scenario-ack-VVaLavIY | 3 | 3 | 0 | 0 | 0 |
| UDP, scenario-udp-q3JnTHNW | 5 | 5 | 0 | 0 | 0 |
| ICMP, scenario-icmp-2eOrvFM2 | 3 | 3 | 0 | 0 | 0 |
| HTTP, scenario-http-29PcYpca | 102 | 102 | 0 | 0 | 0 |
| SYN после новой загрузки, scenario-syn-DiWk0wHX | 2003 | 301 | 1702 | 0 | 0 |

Все показанные генераторы завершились кодом 0. Фоновые SYN могут появляться из-за SSH-снимков/сборщика. Для первого SYN-опыта 509+1495=2004; для последнего 301+1702=2003. В последнем опыте доля drop около 85.0% от учтённых SYN. Это не доля всех сетевых пакетов.

Команда xdp-all THRESHOLD=100 в одном из более ранних выводов завершилась отказом «На ens3 уже есть XDP». Её нельзя считать сменой работающего порога. Условия каждого опыта требуется окончательно связать с последней успешной командой загрузки. Поэтому таблица не приписывает всем опытам пороги 100 или 200 задним числом.

UDP-генератор отправил 1000 пакетов и получил 8 ответов; hping вывел 100% packet loss из-за способа отображения. Это не доказательство отбрасывания UDP данным XDP. В коде нет UDP rate limiter, а SYN-drop в этом опыте не рос.

## 6 Наблюдаемые результаты HTTP и IDS/IPS из локальных reports

Ниже я привожу данные **из сохранённых файлов `reports/`**, а не выдаю их за результаты нового запуска стенда. В Git исходные сырые журналы по умолчанию исключены; в `docs/evidence/` включены обезличенные агрегаты.

| Сценарий | Дата/время (Europe/Moscow) | 200 / 429 | Δhttp.requests | Δhttp.limited | Контроль |
|---|---|---|---|---|---|
| `scenario-http-burst-r2z7cPoV` | 24.10.2026 02:14:25 | 11 / 189 | 201 | 189 | `http.up=1`, `http.status=200` до и после |
| `scenario-http-burst-uguWdSla` | 24.10.2026 13:18:55 | 11 / 189 | 201 | 189 | `http.up=1`, `http.status=200` до и после |

В каждом опыте генератор сообщил о 200 запросах с четырьмя соединениями. Прирост `http.requests=201` включает дополнительный контрольный запрос; это не расхождение с числом запросов генератора. Наличие 429 и Δ`http.limited=189` доказывает срабатывание nginx rate limiting в данных опытах, но не завершает A7 (независимый клиент во время нагрузки) и A1 (чистая установка).

В `ids-acceptance-D111swwj` зафиксированы Δ`ids.alerts=2`, Δ`ids.blocked=1`, контрольный `HTTP=200` и завершение маркированного запроса с кодом curl 28 (тайм-аут). Это согласуется с работой IPS, однако без первичного EVE-события с SID и точной временной привязки запроса нельзя доказать, что именно данное правило вызвало тайм-аут. `ids.parse_errors=24` в обоих снимках — уже накопленное значение, его дельта равна 0.

## 7 Ограничения подтверждения

Нельзя подменять результаты A1/A4/A8/A9/A11/A12 описанием команд, статическим тестом или демонстрационным видео. PCAP и подготовленный образ отсутствуют в компактном архиве, поэтому их контрольные суммы и содержимое здесь не подтверждаются. Результаты опубликованы с указанием происхождения и без приватных логов.
