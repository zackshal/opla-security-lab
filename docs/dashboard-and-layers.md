# Автоматическая панель, HTTP-защита и границы L2–L7

**Русский** · [English](dashboard-and-layers.en.md)

Здесь я описываю дополнительный уровень наблюдаемости, который использовал в OPLA: метрики XDP, события IDS/IPS и состояние HTTP-сервиса. Для меня важно разделять измеренный результат и значение, предусмотренное конфигурацией.

## Что означает XDP attached

Это булев показатель подключения одной программы к ens3 victim: 1 — подключена, 0 — отключена. Это не количество датчиков и не число механизмов защиты. После обновления каждая собираемая метрика представлена отдельным виджетом или таблицей событий. Данные интерфейса, HTTP и XDP разделены по происхождению.

## Развёртывание на существующем стенде

Эта инструкция соответствует текущим исходникам. Если патчи уже применены, не накладывайте их повторно. Команды на хосте из корня проекта:

```bash
make check
export LAB_DIR="$(python3 bin/state.py --latest)"
make ready
make monitoring-up
bash bin/observability-up.sh
```

Предварительно смените начальный пароль Zabbix. observability-up последовательно останавливает сборщик, устанавливает HTTP-политику с nginx -t/reload, развёртывает collect.py, запрашивает пароль API, создаёт/обновляет объекты и запускает сбор. Образы не меняются, ВМ не пересоздаются. При нескольких стендах задайте LAB_DIR явно. После make up нового экземпляра повторите настройку.

Управляемый dashboard текущего узла обновляется целиком; ручную панель клонируйте под другим именем. Статус фактической апробации указан в run-protocol.md. Снятие отслеживания PDF и публикация описаны в release.md.

## Что создаётся автоматически

49 items: 34 исходных показателя и 15 зависимых скоростей; 5 графиков, 23 триггера и 5 страниц dashboard.

| Страница | Содержание |
|---|---|
| XDP and events | XDP attached/mode, SYN/pass/drop, XDP scan policy и события, графики и история Problems |
| HTTP protection | Доступность HTTP, статус, latency, JSON-журнал, 429/5xx и скорости |
| Interface traffic | RX packets/bytes, pps/Bps и графики интерфейса |
| IDS and IPS | Suricata enabled/up, alerts/blocked, ошибки EVE и потери capture |
| Port-scan detection | Состояние пассивного датчика, активные источники, пороговые события, evictions и детали |

Контроль в Data collection → Hosts → текущий opla-ID → Items: 49 элементов. В Latest data сбросьте старые фильтры имени, выберите тот же узел; ожидаются ключи xdp.*, http.*, net.*, ids.*, scan.*. Метки времени должны обновляться. В графиках выберите последние 15 минут. Код статуса 0 означает отсутствие HTTP-ответа в локальной проверке.

HTTP-проверка выполняется с victim на 127.0.0.1:80, поэтому не заменяет curl с client и не проверяет сетевой путь attacker→victim. Проверка выполняется при каждом снимке и сама создаёт небольшой HTTP-трафик. Её запросы входят в HTTP-счётчик. Время — в микросекундах, не миллисекундах. RX-показатели берутся из sysfs драйвера: они не гарантируют учёт всех пакетов до native XDP.

Имена и wire keys описаны в monitoring/catalog.py. Для нового показателя нужны и определение item, и реальный источник данных; создание пустого item само по себе ничего не измеряет.

## Правила обнаружения

| Условие | Событие |
|---|---|
| attached=0 | XDP отключена |
| Нет loaded 60 секунд | Сборщик не передаёт данные |
| drop.rate был >0 за 30 секунд | Есть отбрасывание SYN |
| map_full.rate был >0 за 30 секунд | Карта источников не вместила новый адрес |
| fragment_drop.rate был >0 за 30 секунд | Отброшен фрагментированный TCP |
| Пики syn.rate>500 и drop.rate>100 за 30 секунд | Высокая SYN-нагрузка с отбрасыванием |
| JSON-журнал отсутствует | HTTP-телеметрия недоступна |
| http.limited.rate был >0 за 30 секунд | nginx ограничивал HTTP-запросы |
| http.errors5xx.rate был >0 за 30 секунд | Наблюдались серверные HTTP-ошибки |
| Вырос parse_errors | Журнал не соответствует JSON-формату |
| Последние три локальных HTTP-проверки неуспешны | HTTP локально недоступен |
| Последние три локальные проверки >500 мс | HTTP локально замедлен |

30-секундное окно удерживает короткий всплеск на экране. Две пиковые скорости в правиле давления могут относиться к разным снимкам одного окна: это операционный индикатор, не доказательство корреляции отдельных пакетов. Наличие события rate limiting означает срабатывание политики, а не доказательство злого умысла. Порог нужно выбирать по нормальному трафику и проверять ложные срабатывания.

Пороги задаются в monitoring/policy.json и применяются повторным make monitoring-configure. Настройки предотвращения задаются отдельно: THRESHOLD при сборке XDP и limit_req в security/nginx/opla-l7.conf. Изменение триггера Zabbix не меняет фильтрацию пакетов.

## Реальная L7-политика

В /etc/nginx/conf.d/opla-l7.conf устанавливаются:

- ограничение HTTP по IP клиента: 5 запросов/с, burst=10, nodelay;
- код 429 при отказе ограничителя;
- таймеры чтения заголовков/тела и отправки 10 секунд;
- размер тела не более 1 MiB;
- отдельный JSON-журнал со статусом, источником, методом, URI, временем и limit_req.

Это учебные пороги, они могут ограничить легитимного клиента или группу за NAT. Лимитер не защищает от SQLi/XSS и не является WAF. Таймеры ввода-вывода не заменяют полную защиту от всех разновидностей медленных запросов. У дочернего server/location с собственными limit_req или access_log правила наследования могут изменить поведение. Конфигурация рассчитана на стандартный Debian nginx этого стенда: проверьте effective nginx -T и эксперимент, особенно если меняли server-блок.

Сборщик считает именно limit_req=REJECTED, а не все ответы 429 подряд. Он читает новые полные JSON-строки с курсором и блокировкой в /var/lib/opla-telemetry, сохраняет накопительные счётчики между запусками. Обрабатывает изменение inode и усечение файла, не считает прочитанное дважды. За один опрос читает не более 1 MiB. При ротации непрочитанный хвост прежнего файла может потеряться; это учебный сбор агрегатов, не гарантированная доставка каждого журнала. После удаления state-файла возможен пересчёт текущего журнала: без причины его не удаляйте. Отдельную политику ротации этого JSON-журнала для длительной эксплуатации ещё нужно настроить.

В Zabbix отправляются агрегаты и снимки при изменениях, не каждая строка access log. Источники и URI отдельного запроса смотрите в JSON-журнале victim. Автоматического пер-IP dashboard и базы всех пакетов это обновление не создаёт.

## Эксперименты и ожидаемые доказательства

### A. SYN и режим XDP

```bash
make xdp-stats
bash bin/traffic-scenario.sh syn
```

Должны увеличиться SYN/drop, появиться всплеск на XDP-странице и событие отбрасывания. Порог загруженной программы берите из последней успешной загрузки, не из неудачной пересборки.

### B. HTTP через постоянные соединения

```bash
bash bin/security-http-test.sh
```

Отправляется ровно 200 запросов четырьмя работниками с повторным использованием HTTP-соединений. Это уменьшает влияние SYN-лимитера. Ожидаются HTTP 200 и 429, прирост http_requests и http_limited, событие HTTP requests rate limited и график на HTTP-странице. Время и фактические количества сохраняются в reports/scenario-http-burst-*. Не утверждайте точное число отказов заранее. Transport error не равен 429 и требует отдельного разбора.

Параллельно на client выполняйте обычный curl раз в секунду: у него другой IP, поэтому его результаты оцениваются отдельно.

### C. Восстановление после нагрузки

После окончания опыта дождитесь более 30 секунд: скорости ограничений должны стать 0, события восстановиться, накопительные счётчики сохраниться. Локальная HTTP-проверка должна давать 200.

### D. Контроль отсутствия телеметрии

```bash
make monitoring-stop
```

Подождите более 60 секунд и проверьте Collector has no data в Zabbix. Затем:

```bash
make monitoring-start
```

Ожидайте восстановление свежих значений. Это контрольный сбой сборщика, не компьютерная атака.

### E. Просмотр журналов

На хосте:

```bash
export LAB_DIR="$(python3 bin/state.py --latest)"
lab_id="$(python3 bin/state.py "$LAB_DIR" LAB_ID)"
tail -n 3 "monitoring/runtime/$lab_id/events.jsonl"
journalctl --user -u "opla-monitor-$lab_id.service" -n 30 --no-pager
make ssh VM=victim
```

Внутри victim:

```bash
sudo nginx -T
sudo tail -n 20 /var/log/nginx/opla-security.jsonl
sudo tail -n 20 /var/log/nginx/error.log
sudo bpftool prog show pinned /sys/fs/bpf/opla/program
exit
```

Для проверки доставки по одному ключу остановите сборщик, выполните python3 monitoring/diagnose.py --lab "$LAB_DIR", затем снова запустите сборщик. Ожидается 34 ACCEPTED, включая xdp.*, http.*, net.*, ids.*, scan.*. После изменения preprocessing дождитесь двух свежих снимков, чтобы появились скорости.

## Покрытие L2–L7 и другие утилиты

| Уровень / сценарий | Наблюдение и тестовые средства | Предотвращение | Статус данного проекта |
|---|---|---|---|
| L2, ARP spoofing, подмена MAC | tcpdump -e -n arp, ip neigh, arping | Фильтрация на bridge по порту/MAC/IP, привязки, DAI в аппаратной сети | Автоматической защиты от ARP spoofing здесь пока нет |
| L2, VLAN | Разбор тегов, tcpdump -e, подготовленные кадры | Изоляция портов/bridge и разрешённых VLAN | Парсер XDP понимает до двух тегов; это не защита от всех VLAN-атак |
| L3, ICMP/фрагменты | hping3, tcpdump, ICMP-ответы | Явная политика фрагментов и лимиты ICMP | IPv4/TCP-фрагменты отбрасываются XDP; ICMP не ограничивается |
| L4, SYN | hping3, bpftool, ss -nt state syn-recv | Существующий XDP per-IP SYN rate limit | Реализовано и уже наблюдалось на стенде |
| L4, UDP/ACK | hping3 --udp / -A, ss, tcpdump | Отдельные лимиты/ACL, stateful firewall | SYN-политика их не блокирует; эти опыты показывают границу |
| L4, сканирование | Nmap с небольшим числом портов; Suricata IDS | ACL, разрешённые сервисы; IPS по подходящим правилам | В публичной реализации имеется отдельная XDP distinct-port scan policy; режим observe/block проверяется самостоятельно |
| L5–L6, TLS | openssl s_client, curl -v, журналы TLS | TLS-политика на точке завершения, лимиты handshakes | HTTPS пока не развёрнут; XDP не видит расшифрованный HTTP |
| L7, частые HTTP-запросы | Новый keepalive-тест, curl, JSON access log | nginx limit_req, 429 | Конфигурация и сбор метрик добавлены этим обновлением |
| L7, SQLi/XSS | Тестовое веб-приложение, WAF audit log | Параметризованные запросы, кодирование вывода, ModSecurity/CRS | WAF и уязвимое приложение в этот патч не входят |

Уровни OSI здесь используются как ориентир. Один пакет затрагивает несколько уровней, а слово «предотвращение» требует подтверждения фактического drop/reject, а не только появления alert.

Для проверки нескольких сервисов текущего victim можно отдельно использовать Nmap (требуется установить в подготовленную attacker): nmap -sT -Pn --max-rate 20 --max-retries 0 --host-timeout 20s -p 22,80,443 100.64.0.3. Подставьте адрес из state.env, если он другой. Это ограниченное сканирование учебного узла, не проверка защиты всех портов. Нет открытого сервиса — не значит, что пакет отбросил XDP.

В security/suricata/opla.rules добавлены три примера IDS-правил: интенсивные SYN, UDP и HTTP GET. Это дополнительные примеры для отдельного модуля Suricata, не автоматически включённый IDS. Они используют HOME_NET из конфигурации; для этого стенда задайте /29 из state.env. Alert не предотвращает передачу пакета. Режим IPS и drop требуют отдельной настройки пути трафика и проверки. Не заменяйте alert на drop механически: detection_filter ограничивает события и не является эквивалентом XDP rate limiter.

Если Suricata установлена, сначала проверьте её версию и синтаксис правил через suricata -T -c /etc/suricata/suricata.yaml -S /абсолютный/путь/opla.rules. Фактический режим IDS/IPS подтверждается отдельным протоколом; наличие правил само по себе не доказывает блокировку. Публичный сборщик содержит источники IDS/scan; реальный приём EVE и свежесть данных требуют отдельной проверки на стенде.

Установка Suricata/WAF/новых утилит требует обновления подготовленного образа с доступом к репозиториям и последующего повторного развёртывания. У изолированных рабочих ВМ Интернета намеренно нет. Не меняйте используемый backing image через virt-customize, пока стенд работает.

## База данных

Для xdp.* остаётся monitoring/sql/inspect.sql. Для всех новых метрик используйте monitoring/sql/security-overview.sql:

```bash
lab_id="$(python3 bin/state.py "$LAB_DIR" LAB_ID)"
docker compose --env-file monitoring/.env -f monitoring/compose.yaml exec -T db psql -U zabbix -d zabbix -v "host_name=opla-$lab_id" < monitoring/sql/security-overview.sql
```

Запрос читает каталог и последние значения через LATERAL по каждому item. История хранится отдельно: целые — history_uint, скорости — history, mode — history_str, события — history_log. Ни один SQL здесь не изменяет БД.

## Фиксация и откат

Изменения в публичном GitHub вносятся через отдельную ветку и Pull Request. Коммит для уже опубликованного расширения повторно создавать не требуется.

Для снятия HTTP-политики: bash bin/security-http.sh remove. Это удаляет только наш nginx-файл, проверяет конфигурацию и reload. Для полного возврата версии сначала остановите сборщик и снимите HTTP-политику, затем git revert коммита обновления, make xdp-deploy, make monitoring-configure и make monitoring-start. Старые добавленные items в БД могут сохраниться после отката: настройщик их не удаляет. Политика Zabbix не должна считаться действующей после удаления конфигурации nginx лишь потому, что старый JSON-журнал ещё существует.

В среде подготовки НЕ запускались живой Zabbix API/виджеты, nginx -t, новый HTTP-тест на ВМ, Suricata и kernel verifier. Для ядра C-код этим патчем не меняется. Локальное прохождение unit-тестов не подменяет проверку на вашем стенде.
