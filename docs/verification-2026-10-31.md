# Проверка OPLA от 31 октября 2026 года

## Итог

Автономные проверки исходников проходят. Работоспособность полного стенда и
живучесть под реальной нагрузкой **не подтверждены новым live-прогоном**.
Критерий сдачи по ТЗ остаётся BLOCKED: необходим чистый выделенный Linux-хост,
образы трёх ролей и протокол единого опыта. Это проверка учебного OPLA
QEMU/XDP/Suricata/nginx/Zabbix, а не отдельного дипломного проекта.

Исходная ревизия: `382962070a685a565915ebd79f7cc5d981634b34`.
Источник: предоставленный `opla.tar.gz` без QCOW2 и шестистраничное ТЗ.
Архивные виртуальные окружения не использовались. Исходная незакоммиченная
запись `docs/evidence/local-verification-2026-10-31.md` сохранена без изменений
и не включена в новый коммит. Её результаты относятся к другому окружению.

разрешённые локальные Unix-сокеты. Возврат OK при skipped не закрывает эти случаи.

## Найденные и исправленные дефекты

1. `tests/test_service_process_runtime.py`: создание socket выполнялось до
   блока обработки EPERM. В среде, запрещающей socket(), восемь тестов падали
   до проверки бизнес-логики. Создание и bind теперь входят в один capability
   probe; ресурс закрывается только после успешного создания. Три регрессионных
   теста проверяют отказ create, отказ bind и сохранение неожиданной ошибки
   EMFILE. Продуктовые ограничения и проверки доступа не ослаблены.
2. `tools/export-pdf-gost.py`: явная Markdown-подпись таблицы печаталась обычным
   абзацем, после чего exporter добавлял вторую подпись. Теперь явный заголовок
   используется единожды с последовательной нумерацией и удерживается с таблицей.
   Заголовки разделов удерживаются с первым блоком содержимого.

## Работоспособность и живучесть

Прочитаны реальный Makefile, lifecycle journal и orchestrator, CI, тесты
сокетов, runtime inventory и документация приёмки. Journal проверяет личность
лаборатории, порядок этапов, timestamps и evidence; сохранение использует
временный файл, fsync и replace. Offline orchestrator требует независимые
probes и ограничивает время этапов. Тесты моделируют ошибки создания,
прерывание, блокировки, восстановление configure и отсутствие telemetry.
Это свидетельство обработки моделируемых отказов, а не измерение MTTR,
потерь пакетов или доступности реального HTTP-сервиса.

Не проверены: kernel BPF verifier и attach, KVM/QMP, загрузка cloud-init,
реальные bridge/TAP/nft, IDS/IPS под трафиком, доставка Zabbix API,
восстановление PostgreSQL и VM-дисков, reboot и продолжительная нагрузка.
Пакетный C harness не заменяет выполнение eBPF в ядре.

## Соответствие ТЗ

Материалы уже содержат методичку, две схемы, инструкцию, шаблон отчёта,
5 практических заданий, 12 вопросов самопроверки и 15 тестовых вопросов.
Подробная [матрица требований](requirements-traceability.md) остаётся
авторитетной картой. Закрытый ключ преподавателя не публикуется.

Остаются незакрытыми точные версии и copyright всех фактически установленных
компонентов, включая Nmap; воспроизведение с нуля; фактическая изоляция;
согласование темы; единый отчёт опыта с PCAP, hashes и восстановлением.
Таблица целевых версий не равна manifest апробированного стенда.

## Порядок завершения приёмки

1. На выделенном допущенном хосте повторить автономные тесты от обычного
   пользователя. Сохранить все причины skipped; сервисные тесты должны реально
   выполняться. Проверить текущий CI отдельно: Docker job по умолчанию root,
   поэтому его зелёный статус может содержать пропуски rootless-тестов.
2. Следовать [подготовке хоста](test-host-spec.md),
   [установке](local-system-install.md) и [методичке](methodology.md).
   Сохранить commit, SHA-256 образов, пакеты и container digests.
3. По [E2E-плану](e2e-test-plan.md) проверить create → ready → activate,
   три роли, management/data separation, XDP и Suricata.
4. Запустить только конечный сценарий внутри data network. Непрерывно измерять
   HTTP с client до, во время и после нагрузки. Сохранить timestamps, интервалы
   отсутствующих данных, HTTP codes/latency, XDP counters и EVE.
5. Провести разрешённые fault/recovery опыты и
   [восстановление backup](backup-restore.md). Измерить время восстановления
   и потери evidence. Порог допустимости согласовать до опыта: ТЗ числовых
   SLO не устанавливает.
6. Выполнить очистку выбранной lab, проверить отсутствие её ресурсов и
   сохранность независимых workloads. Заполнить [протокол](run-protocol.md).

В `AGENTS.md` явно требуется отдельный разрешённый хост для этих live-шагов;
они не выполнялись в текущем окружении проверки.

## Документация и публикация

README уже имеет описание, схему, quickstart, ограничения и ссылки на
эксплуатационные материалы. Подход [awesome-readme](https://github.com/matiassingers/awesome-readme)
использован как ориентир навигации и воспроизводимых инструкций, а не как
доказательство качества кода. В README и индексе добавлена ссылка на этот аудит.
Исторические результаты не переименованы в новый опыт.

Remote назначения: `https://gitlab.com/k3rnel_co0n/opla-security-lab.git`.
В архивном Git config задан прокси `socks5h://127.0.0.1:9050`: он недоступен.
Разовый override прокси показал второй блокер: `Could not resolve host: gitlab.com`.
Конфигурация пользователя не изменялась. Нельзя утверждать, что push или pipeline
состоялись. Подготовлена отдельная ветка `audit/2026-10-31`; публиковать без force.

Из собственного клона, после проверки приложенного patch:

```bash
git switch -c audit/2026-10-31
git am /path/to/opla-audit.patch
python3 -m compileall -q bin tests
make check
python3 tools/check-documentation.py
git diff --check
git push gitlab HEAD:refs/heads/audit/2026-10-31
```

Если ветка уже существует, выбрать новое имя; при конфликте patch сначала
сопоставить историю, не сбрасывать локальные изменения. Публикация ветки
позволяет review перед merge в main; автоматический deploy не запрашивается.
