# Защита учебного HTTP сервера от SYN flood средствами eBPF и XDP

Практическая работа по дисциплине «Обнаружение, предупреждение и ликвидация последствий компьютерных атак».

Разработчик: Шалашов Захар, группа БББО-01-23. РТУ МИРЭА. Москва, 2026.

## 1 Аннотация

В работе нужно развернуть три виртуальные машины, проверить доступность HTTP-сервера и сравнить обработку SYN-пакетов до и после включения XDP. Затем нужно подключить Zabbix, получить графики и объяснить результат. Цель работы — научиться связывать сетевой признак атаки, правило фильтрации и наблюдаемые показатели.

Студент изучает TCP handshake, читает небольшую программу на C, изменяет порог ограничения и проверяет, не пострадал ли обычный клиент. Для выполнения нужны основы Linux, IPv4, SSH и TCP. Ориентировочная продолжительность — два занятия по 90 минут без учёта первого скачивания образов.

## 2 Теоретическая часть

### 2.1 Как возникает SYN flood

При обычном установлении TCP-соединения клиент отправляет SYN, сервер отвечает SYN+ACK, после чего клиент подтверждает соединение пакетом ACK. Серверу приходится хранить состояние соединения, которое ещё не установлено окончательно. Большой поток начальных SYN способен создавать нагрузку на эту очередь, процессор и сетевые ресурсы. Сам по себе SYN не означает атаку: его отправляет каждый обычный TCP-клиент.

В лабораторной используются два независимых источника. Attacker отправляет много SYN на порт 80, а client делает обычные HTTP-запросы. Так можно увидеть не только рост отбрасываний, но и доступность сервиса для другого адреса. Нагрузка ограничена числом пакетов. При таком объёме исходная система может не потерять доступность: это допустимый результат, а не доказательство отсутствия атаки вообще.

### 2.2 Что делает eBPF и где работает XDP

eBPF позволяет загрузить программу в ядро после проверки verifier. XDP — точка обработки входящих кадров. Программа возвращает действие: например, XDP_PASS для продолжения обработки или XDP_DROP для отбрасывания.

В native-режиме XDP работает в поддерживающем его драйвере, до обычной обработки пакета сетевым стеком. Generic XDP работает над уже созданным skb. Поэтому нельзя приписывать generic те же расходы и производительность, что native. В этой работе сравнивается прежде всего поведение правила; производительность без отдельной методики не оценивается.

### 2.3 Алгоритм ограничения

Программа рассматривает IPv4 TCP с SYN=1 и ACK=0. Для каждого source IP хранится начало окна и число SYN в нём. Окно длится 1 000 000 000 нс. Первые 100 SYN пропускаются, начиная со 101-го программа возвращает XDP_DROP. Первый пакет нового окна получает count=1. SYN+ACK не относится к этому потоку и пропускается.

Состояние одного IP находится в одной hash-map и обновляется под bpf_spin_lock. Это предотвращает одновременное изменение начала окна и счётчика разными CPU. Для графиков используется другая map: накопительные per-CPU счётчики. Сборщик складывает значения всех CPU. Разность накопительных значений, делённая на фактический интервал, даёт скорость в пакетах в секунду.

Это фиксированные окна, отсчитываемые от первого пакета IP. Около границы двух окон возможен короткий всплеск до двух порогов. Поэтому правило не задаёт точный лимит для любого скользящего интервала в одну секунду.

### 2.4 Обнаружение и реагирование

Признак срабатывания — увеличение накопительного счётчика drop. Zabbix рассчитывает скорость drop и создаёт событие при положительном значении. Отдельные триггеры показывают отсутствие XDP и отсутствие данных сборщика. Ошибка SSH не превращается в ложное сообщение о нулевой нагрузке.

Реагирование в работе состоит из ограничения SYN, остановки генератора, проверки восстановления HTTP и сохранения результатов. Отключение XDP используется для сравнения. Оно само по себе не устраняет причину внешней нагрузки.

### 2.5 Другие подходы и границы метода

SYN cookies уменьшают потребность хранить состояние начального handshake. nftables позволяет фильтровать и ограничивать трафик в сетевом стеке. IDS анализирует наблюдаемый поток и формирует уведомления; XDP-программа принимает решение о пакете непосредственно в точке обработки. Эти подходы могут дополнять друг друга.

В данной реализации фильтр считает начальные SYN всех TCP-портов по одному source IP. Он не определяет намерения клиента и не анализирует HTTP. За NAT несколько пользователей делят один лимит. Распределённый поток с небольшим числом пакетов на каждый IP может пройти. Подмена адресов и заполнение таблицы также ограничивают применимость решения.

В hash-map максимум 1024 адреса. Старые записи автоматически не удаляются: при невозможности добавить новый адрес SYN от него отбрасывается, а map_full увеличивается. Это выбранный режим отказа для учебного стенда. Возврат к пустой таблице — выгрузка и новая загрузка XDP. Реальную защиту с таким поведением нельзя оценивать только по одному успешному запуску нагрузки.

Поддерживается разбор до двух VLAN-тегов и переменной длины IPv4-заголовка. Фрагментированный IPv4 TCP целиком отбрасывается: его счётчик отдельный. IPv6, UDP и прочие протоколы этим SYN-ограничителем не защищаются. На ВМ IPv6 отключён настройкой стенда. Часть некорректных кадров отбрасывается до счётчиков SYN, поэтому syn=pass+drop относится только к распознанным начальным SYN, а не ко всем входящим кадрам.

## 3 Лабораторный стенд

![Рисунок 2 — Схема стенда и мониторинга](figures/topology.svg)

Все ВМ подключены к одному мосту br-opN. Создаётся свободная подсеть /29 из 100.64.0.0/10 с проверкой пересечения с маршрутами хоста. Адреса приведены как пример первого свободного блока; фактические значения записаны в state.env.

Таблица 1 — Пример адресации

| Участник | Пример адреса | Назначение |
|---|---|---|
| Хост и мост | 100.64.0.1/29 | SSH к ВМ и сбор метрик |
| attacker | 100.64.0.2/29 | Ограниченная SYN-нагрузка |
| victim | 100.64.0.3/29 | Nginx и XDP, 2 vCPU и 2 ГБ RAM |
| client | 100.64.0.4/29 | Проверка HTTP, 1 vCPU и 512 МБ RAM |
| Zabbix | 127.0.0.1:8080 на хосте | Веб-интерфейс мониторинга |

У attacker выделены 1 vCPU и 1 ГБ RAM. Рекомендуемые ресурсы хоста: 4 ядра, 12 ГБ RAM и 30 ГБ свободного диска; аппаратная виртуализация и доступ к /dev/kvm обязательны. Подготовка образа и контейнеров требует сети. Во время опыта у ВМ нет default route; nftables дополнительно запрещает маршрутизацию через хост и новые обращения ВМ к службам хоста. Разрешаются ответы на соединения хоста и DHCP. Ранее установленные firewall-правила хоста тоже могут влиять на связь.

Полный перечень средств, лицензий и источников находится в software.md. ВМ работают на Debian 12, мониторинг использует Zabbix 7.0.19 и PostgreSQL 16.10. Это выбранные версии контейнеров, а не заявление о выполненной апробации. Фактические версии пакетов и ядра нужно приложить после запуска командой make versions.

## 4 Подготовка чистой системы

### 4.1 Установка средств на хост

Для хоста Debian 12 amd64 выполните команды из листинга 1. Docker используется как свободный Docker Engine вместе с Compose, без Docker Desktop. Если выбран другой Linux, команды установки пакетов нужно адаптировать и записать отличие в протоколе апробации.

Листинг 1 — Установка зависимостей

```bash
sudo ./bin/install-host.sh
```

Скрипт устанавливает Compose v2 из официального apt-репозитория Docker. Он рассчитан на чистый Debian 12; ранее установленные конфликтующие пакеты Docker следует проверить до запуска. После установки настройте доступ пользователя к Docker.

Листинг 2 — Проверка среды

```bash
sudo usermod -aG docker "$USER"
# Перезайдите в пользовательскую сессию для применения группы.
docker compose version
test -c /dev/kvm && ls -l /dev/kvm
systemctl --user status
ssh-keygen -t ed25519
```

Ожидаемый результат: Compose v2 доступен, /dev/kvm существует, пользовательская systemd-сессия работает. Если SSH-ключ уже создан, используйте его; не перезаписывайте существующий ключ. По умолчанию скрипты используют ~/.ssh/id_ed25519. Для нестандартного ключа задайте SSH_KEY для команд клиента. Создание ВМ с другим public key: sudo env SSH_KEY_PUB=/абсолютный/путь/ключ.pub ./bin/create-lab.sh.

### 4.2 Подготовка образа

Из корня проекта выполните листинг 3. bootstrap скачивает официальный Debian genericcloud и проверяет SHA512 из опубликованного списка по HTTPS. Проверка не использует отдельную подпись списка. Затем prepare-image устанавливает пакеты в копию образа через virt-customize. Образ расширяется до 10 ГБ; для выбранного Debian genericcloud корневая ФС ожидается в /dev/sda1. Если разметка другого образа отличается, virt-resize завершится ошибкой: проверьте virt-filesystems -a images/debian-12-base.qcow2 --all --long. В гостевой системе сохраняется /etc/opla-packages.txt.

Листинг 3 — Создание образа для ВМ

```bash
make bootstrap
make image
cat images/downloaded.sha256
cat images/prepared.sha256
```

Ожидаемый результат: images/debian-12-base.qcow2 и images/debian-12-xdp.qcow2. Образ alpine больше не нужен. Первый build зависит от состояния Debian-репозитория: сохраните подготовленный образ и его хеш вместе с итоговым комплектом, если нужна идентичная среда у всей группы. Старый подготовленный образ автоматически не перезаписывается.

### 4.3 Проверка исходников

Листинг 4 — Автоматические проверки

make check

Итог cloud-init должен быть done. При ошибке используйте make console VM=victim и journalctl для соответствующей qemu-службы.

### 5.2 Проверка адресов и изоляции

Листинг 6 — Проверки из ВМ и с хоста

```bash
make ssh VM=attacker
ip -4 address show ens3
ip route
curl --connect-timeout 2 http://1.1.1.1
exit

```

Ожидаемый результат: есть маршрут только в /29, default route отсутствует, внешнее HTTP-соединение не устанавливается, на хосте есть отдельная таблица opla_lab_.... Это не исчерпывающий сетевой аудит: дополнительно проверьте отсутствие маршрутизации к физической сети хоста согласно acceptance.md. Проверка должна предшествовать нагрузке.

### 5.3 Базовая доступность и состояние TCP

Откройте make ssh VM=client. Подставьте фактический VICTIM_IP, показанный при запуске, и выполните листинг 7.

Листинг 7 — Проверка HTTP и очереди соединений

```bash
curl -sS -o /dev/null -w '%{http_code} %{time_total}\n' http://VICTIM_IP/
```

На victim проверьте systemctl is-active nginx и ss -nt state syn-recv. Ожидаемый результат обычного HTTP-запроса — 200. Выполните несколько запросов и сохраните время ответа. До включения XDP проведите базовую нагрузку из пункта 5.7 вручную и повторите HTTP-запросы во время неё. Зафиксируйте результат, даже если деградации не было.

### 5.4 Сборка и загрузка защиты

Листинг 8 — XDP с порогом 100 SYN за окно

```bash
make xdp-all
make xdp-stats
```

Действие: скопировать исходники на victim, собрать clang -target bpf, загрузить программу и привязать её к ens3. Ожидаемый результат: native или generic, затем JSON с loaded=1. Ошибки verifier выводятся в консоль и не скрываются переходом на generic. Maps закреплены в /sys/fs/bpf/opla/maps; после выгрузки pins удаляются.

### 5.6 Проверка наблюдаемости

Листинг 11 — Локальный дашборд и журнал

```bash
make xdp-dashboard

```

В другой консоли найдите фактический LAB_ID по пути стенда и выполните journalctl --user -u opla-monitor-LAB_ID -f. Файл monitoring/runtime/LAB_ID/events.jsonl содержит снимки и ошибки. ### 5.7 Нагрузка и доступность обычного клиента

Листинг 12 — Ограниченный поток SYN

```bash
make xdp-test
```

Действие: attacker отправляет 2000 SYN на порт 80 с интервалом примерно 1 мс. Ожидаемый результат: syn и drop увеличиваются. Скорость реально отправленных пакетов зависит от планировщика и ресурсов ВМ. Не требуйте точного числа отбрасываний сетевого опыта; точная граница порога отдельно проверяется тестом C.

Для более продолжительного наблюдения зайдите на attacker и используйте sudo hping3 -n -S -p 80 -i u1000 -c 20000 VICTIM_IP. Одновременно на client выполните несколько curl-запросов из листинга 7. Ожидается успешный HTTP при достаточных ресурсах стенда; подтвердите это результатами. Если hping3 вернул ненулевой код, скрипт всё равно показывает итоговые счётчики и сохраняет код ошибки. Разберите его отдельно от результата фильтра.

В native XDP отброшенные кадры могут не попасть в tcpdump на victim. PCAP для оценки отправленного потока снимайте на attacker или на мосту хоста. Учтите место захвата при сравнении количества пакетов.

### 5.8 Изменение порога

Листинг 13 — Повторный опыт

```bash

```

Ожидаемый результат: на одинаковом потоке число пропущенных SYN в окне увеличивается. После перезагрузки XDP накопительные счётчики начинаются заново. Zabbix preprocessing «изменение в секунду» пропускает отрицательное изменение; первый новый интервал не нужно трактовать как отрицательную скорость.

Ожидаемый результат: ВМ и мост удалены, правила конкретного стенда удалены, чужие nftables-таблицы не изменены. База Zabbix сохраняется в volume.

Исходные и подготовленные qcow2 не включены в текстовый комплект из-за объёма. Их создаёт инструкция. Исторические контрольные суммы в checksums-original.sha256 относятся к прежнему стенду и не используются для проверки нового образа.

## 10 Возможные проблемы

Таблица 2 — Диагностика

| Признак | Проверка | Действие |
|---|---|---|
| Нет /dev/kvm | Настройки BIOS или nested virtualization | Включить аппаратную виртуализацию |
| SSH connection refused | make console VM=victim | Дождаться загрузки, проверить cloud-init и sshd |
| HTTP не работает | systemctl status nginx на victim | Проверить адрес и журнал nginx |
| Ошибка BPF verifier | Вывод make xdp-load | Проверить ядро, BTF и helpers, сохранить полный журнал |
| Native не поддержан | Ошибка ip link xdpdrv | Загрузчик пробует xdpgeneric; записать режим |
| Нет данных Zabbix | journalctl пользовательской службы | Проверить SSH, host/key, конфигурационный кеш сервера |
| Dashboard пуст | Data collection → Latest data и provisioned.json | Проверить поступление items и повторить configure |
| Накопительный счётчик сбросился | Была выгрузка программы | Разделить временные интервалы опытов |
| map_full растёт | Более 1024 адресов или ошибка добавления | Остановить нагрузку, перезагрузить XDP, объяснить ограничение |
