# Модель угроз и границы применимости

**Русский** · [English](security-model.en.md)

Модель угроз я составил для своего лабораторного стенда OPLA. Я рассматриваю защиту учебного HTTP-сервиса и достоверность результатов опытов; требования к промышленной инфраструктуре и защите реальных пользовательских данных в эту модель не включал.

## 1 Объект и активы

Защищаются доступность учебного HTTP-сервиса и возможность достоверно объяснить поведение фильтра. Дополнительные активы: SSH-ключи, хост KVM, корректность состояния стенда, пароль БД и результаты опытов. Конфиденциальность production-данных и сертифицированная защита ОС не заявляются.

## 2 Нарушитель и доверие

В базовом опыте attacker контролирует свою ВМ и отправляет трафик на victim внутри /29. Администратор хоста, каталог исходников, ключ оркестрации и конфигурация мониторинга считаются доверенными. Злонамеренный root хоста вне модели: он может изменить карты, бинарник, журналы и БД.

Student с NOPASSWD внутри ВМ - осознанное учебное допущение. Изоляция ВМ не доказывает стойкость против выхода из гипервизора. Docker socket и группа docker дают широкие административные возможности. При публикации нельзя переносить локальные ключи/пароли/дампы без проверки.

## 3 Угрозы и меры

| Угроза | Реализованная мера | Ограничение и проверка |
|---|---|---|
| Частые начальные SYN | XDP per-IP fixed window | NAT/распределённые IP; проверить Δdrop и клиента |
| Неожиданные длины/фрагменты IPv4 TCP | Bounds checks, явный fragment DROP | Часть drop не входит в SYN-counter; ядро проверять отдельно |
| Ошибка конкурентного обновления окна | bpf_spin_lock | Mocked tests не доказывают все race conditions |
| Исчерпание source map | Bounded map, fail-closed для нового SYN, метрика map_full | Возможен отказ легитимным новым источникам |
| HTTP-нагрузка внутри соединения | nginx limit_req и таймеры | Не WAF; одинаковые IP делят лимит |
| Потеря телеметрии | Проверка формата, принятого count, nodata | Нет durable queue и гарантии каждого события |
| Исполнение подставленного state.env | Разбор данных и проверка root-owned пути | Доверенный root может изменить состояние |
| Выход трафика за стенд | Нет default route и scoped nftables | Сетевые пробы ещё должны подтвердить конфигурацию |
| Утечка пароля БД/ключей | .gitignore, getpass, локальные bind | История Git и внешние архивы проверяются отдельно |

## 4 Покрытие L2-L7

L2: отдельного ARP/MAC anti-spoofing нет; разбор VLAN не предотвращает все VLAN-атаки. L3/L4: базовый XDP ограничивает IPv4 SYN и отбрасывает фрагментированный TCP; UDP, ICMP, IPv6 и ACK rate limiting базовым SYN-правилом не реализованы; сканирование имеет отдельную политику. L5/L6: TLS в текущем стенде не развёрнут. L7: подготовлены nginx rate limiting и HTTP-телеметрия; SQLi/XSS потребовали бы приложения/WAF и собственной апробации.

Suricata rules - примеры отдельного IDS-модуля. В публичной реализации есть отдельные сценарии IDS/IPS Suricata и соответствующие источники телеметрии; их живое состояние проверяется отдельно. Само слово alert не означает предотвращение. Контрольные HTTP/UDP/ACK-потоки нельзя выдавать за подтверждение универсальной защиты.

## 5 Эксплуатационные ограничения

Нет подписей телеметрии, цепочки хешей или защиты БД от администратора. Это отдельная тема, не реализованный модуль OPLA. Нет измерения предельного pps, latency overhead, автоматического восстановления стенда после перезагрузки и полной записи PCAP в БД.

Для длительной эксплуатации нужно настроить ротацию HTTP JSON-журнала, ограничения диска и более узкий агентский доступ. Для production потребуются отдельное рассмотрение TLS/auth, хранения секретов, обновлений, политик минимальных привилегий и независимая проверка. Эти пункты не подменяют пригодность проекта для учебной демонстрации.
