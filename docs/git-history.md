# Исходная история в публичном GitHub

## Почему появился один коммит

Первая публикация GitHub была отдельным исходным snapshot, чтобы не отправлять приватную .git историю с ранее отслеживавшимися PDF/DOCX. Поэтому public main начинается с root commit fecbfac. Исходная история в ~/vim/opla-ebpf-reviewed и GitLab не удалялась.

## Как добавляется история

Комплект содержит history.py, который выполняет два отдельных действия:

1. Read-only экспортирует из текущей ветки исходного checkout историю только путей, уже отслеживаемых публичным checkout. Git fast-export/fast-import создают отдельный filtered repository. Остальные файлы и refs не копируются.
2. После проверок добавляет filtered history как второго родителя merge commit публичного main. Стратегия ours сохраняет текущую публичную файловую систему. Это присоединение происхождения, не откат к старой реализации и не разрешение кодовых конфликтов.

Force push не используется. Начальный public commit остаётся. GitLab refs не меняются. Хеши старых коммитов могут измениться после фильтрации, часть коммитов без изменений выбранных путей исчезнет. Авторы, даты и сообщения сохранившихся коммитов сохраняются и станут публичными. Это не искусственное создание задним числом новых этапов работы.

Исторические подписи после преобразования не переносятся как доказательство подлинности. Новое merge-связующее звено тоже не является независимым криптографическим доказательством происхождения исходников.

## Порядок действий

Сначала закоммитьте текущие правки документации в public checkout; его working tree должен быть чистым. Установите scanner:

```bash
sudo apt-get install gitleaks
```

Из каталога распакованного комплекта:

```bash
history_review="$HOME/opla-archive/history-review-$(date +%Y%m%d-%H%M%S)"
python3 history.py prepare \
  --source "$HOME/vim/opla-ebpf-reviewed" \
  --public "$HOME/vim/opla-security-lab-public" \
  --work "$history_review"
```

Команда требует gitleaks и проверяет exact GitHub origin zackshal/opla-security-lab. Ветка source берётся из её текущего HEAD; незакоммиченные source-файлы в историю не попадут. В review directory сохраняются filtered repository, результаты scan и audit.json. В потоковом экспорте содержатся только выбранные пути, но до завершения scan каталог всё равно считается приватным.

Проверки включают все reachable commits/blobs, а не только конечный tree: запрещённые paths/modes, объекты больше 20 MiB, характерные токены/private keys, затем Gitleaks всей истории. При находке ничего не merges/pushes. Не добавляйте blanket allowlist ради прохождения scan; найденные данные сначала исследуются локально и при необходимости отзываются/редактируются в отдельной фильтрации.

Просмотр:

```bash
git -C "$history_review/filtered" log --graph --oneline --all
git -C "$history_review/filtered" log --format='%h %ad %an %s' --date=short
```

Чтобы присоединить проверенную историю и отправить обычным push:

```bash
python3 history.py merge \
  --public "$HOME/vim/opla-security-lab-public" \
  --work "$history_review" --push
```

Перед merge scan выполняется ещё раз, создаётся bundle текущего public repository и проверяется неизменность HEAD. После merge write-tree должен совпасть с прежним tree: старый README или старый код не заменяют текущий. Успешный push запускает новый Actions run на текущем, а не историческом workflow.

Если public HEAD изменился между prepare и merge, создайте новый review directory и повторите prepare. Не перезаписывайте audit.json вручную. При отказе push из-за новых remote commits не используйте --force: сначала сверяйте локальную и remote истории.

При запуске без --push создаётся только локальный merge. Его можно посмотреть перед обычным git push origin HEAD:main. GitHub список commits может группировать merge/history иначе, чем линейный changelog; полную связь видно через git log --graph --all.

## Чего проверка не обещает

Gitleaks и дополнительные шаблоны не доказывают отсутствие любых конфиденциальных данных, включая чувствительные commit messages/имена авторов. Проверьте личные данные перед публикацией истории. Фильтрация по нынешним путям не прослеживает автоматически все исторические переименования. Исходный приватный repository и backups остаются на месте; их очистка — отдельная операция.
