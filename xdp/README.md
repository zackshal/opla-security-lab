# XDP: обнаружение и предотвращение SYN-флуда

## Зачем этот модуль

Лабораторная демонстрирует **rate-limiting на уровне XDP** для SYN-флуда.
XDP-программа цепляется к `ens3` жертвы и **отбрасывает пакеты до попадания
в сетевой стек ядра**. Это быстрее, чем `iptables`/`nftables`, потому что
работает в драйверном (native) или SKB (generic) режиме без аллокаций.

## Файлы и их роль

| Файл | Роль | Почему именно так |
|---|---|---|
| `xdp_ddos_protect.c` | XDP-программа: rate-limit по source IP | Парсит Ethernet/IP/TCP, считает SYN-пакеты в BPF-map, дропает при превышении порога |
| `Makefile` | Компиляция C → BPF-объект | `clang -target bpf`; `-I/usr/include/bpf` для `bpf_helpers.h`; `-D__TARGET_ARCH_x86` для BPF CO-RE |
| `lib.sh` | Общие функции (SSH, victim IP) | Один источник правды для всех скриптов; **массив** SSH-опций — избегаем бага с `-i "строка"` |
| `deploy.sh` | Копирование источников на victim | Хост хранит файлы (git), victim собирает — `clang` есть только в гостевом образе |
| `load.sh` | `ip link set dev ens3 xdp obj ...` | Native-режим; fallback на `generic`, если драйвер не поддерживает |
| `unload.sh` | `ip link set dev ens3 xdp off` | Чистая выгрузка — нужно для идемпотентности |
| `test.sh` | `hping3` с attacker + `bpftool map dump` на victim | Воспроизводимая атака 10 сек, ожидаемый результат — счётчики в `rate_limit_map` |
| `dashboard.py` | TUI-дашборд (SSH → `bpftool`) | Видеть в реальном времени, какие IP дропаются; без внешних зависимостей |

## BPF-maps: зачем две

**`rate_limit_map`** — `Hash<u32, u64>`: `source IP → счётчик SYN-пакетов в текущем окне`.
Нужен, чтобы отслеживать «сколько пакетов от данного IP за 1 сек».

**`first_seen_map`** — `Hash<u32, u64>`: `source IP → timestamp первого пакета окна`.
Нужен, чтобы **сбрасывать счётчик** каждые `WINDOW_NS` (1 сек). Без него счётчик рос бы бесконечно, и любой легитимный клиент рано или поздно был бы заблокирован.

**Почему Hash, а не Array:** source IP — 32-битный ключ с произвольными значениями; Array требует индексации `0..N`, а у нас IP из `100.64.0.0/10` (миллионы возможных).

**Почему `max_entries=1024`:** в /29-подсети максимум 6 хостов; 1024 с запасом на distributed SYN-flood (для сценария «много IP»).

## Пороги

| Макрос | Значение | Что означает |
|---|---|---|
| `THRESHOLD` | 100 | Больше 100 SYN за окно → `XDP_DROP` |
| `WINDOW_NS` | `1 000 000 000` (1 сек) | Окно сброса счётчика |

Меняются при компиляции: `make CFLAGS+='-DTHRESHOLD=500'` — материал для практического задания №2.

## Режим XDP: native vs generic

| Режим | Когда | Как проверить |
|---|---|---|
| **Native** | Драйвер поддерживает (virtio_net в QEMU — **не всегда**) | `ip link show ens3 \| grep -oE 'xdp[a-z]*'` → пусто |
| **Generic** | Fallback (SKB) | `ip link show ens3 \| grep -oE 'xdp[a-z]*'` → `xdpgeneric` |

Оба режима **функционально идентичны** для лабораторной. Native быстрее, но в QEMU с virtio обычно грузится generic. В методичке — честно указать.

## Почему не пишем через `libxdp` / `xdp-loader`

Для учебной задачи `ip link set ... xdp obj` — самый прозрачный способ: студент видит **как** программа привязывается к интерфейсу. `xdp-loader` (из `xdp-tools`) делает то же самое, но с абстракцией, которая скрывает механику.
